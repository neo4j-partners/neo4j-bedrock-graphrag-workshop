== Two Halves of One Graph

The graph you explored in Part 1 (companies, products, risk factors, asset managers) is the **structured half**. The Lab 1 seed load also added the **unstructured half**: Document and Chunk nodes with embeddings, linked by `FROM_DOCUMENT` and `NEXT_CHUNK` relationships. Cross-links (`FROM_CHUNK`) connect entities like Products and RiskFactors to the Chunks that mention them.

The `FILED` relationship bridges the two halves: `(Company)-[:FILED]->(Document)`. When graph-enriched search traverses from a chunk to its source document to the company that filed it, it crosses from unstructured text into the structured entities you already know. That traversal chain, `(Chunk)-[:FROM_DOCUMENT]->(Document)<-[:FILED]-(Company)`, is what makes GraphRAG possible.

== The neo4j-graphrag Library

This lab uses the https://github.com/neo4j/neo4j-graphrag-python[neo4j-graphrag] Python library, which provides the building blocks for GraphRAG applications on Neo4j:

* **Retrievers**: `VectorRetriever` and `VectorCypherRetriever` handle embedding the query, running the vector search, and (for Cypher retrievers) traversing the graph to enrich results with structured context. `HybridRetriever` and `HybridCypherRetriever` add fulltext keyword search and re-rank the fused results
* **GraphRAG pipeline**: combines a retriever with an LLM to go from a natural-language question to a grounded answer in a single call
* **LLM and Embedder abstractions**: pluggable providers including Bedrock, OpenAI, Anthropic, Cohere, and Vertex AI
* **Knowledge Graph Construction**: `SimpleKGPipeline` for building graphs from text and PDFs (used in xref:lab2.adoc[Lab 2])
* **Vector index utilities**: `create_vector_index` and `upsert_vectors` for managing Neo4j vector indexes

The library handles the plumbing so you can focus on retrieval strategy rather than low-level Cypher and embedding management.

== Chunks, Embeddings, and Graph-Enriched Search

Most documents are too long for an LLM to process in a single pass. Retrieval-Augmented Generation (RAG) solves this by finding the most relevant pieces of a document and feeding only those to the model. The building blocks are:

**Chunks.** A long document is split into smaller passages called chunks (think of them as paragraphs or short sections). Each chunk is small enough for the system to process individually, but long enough to carry useful context. Chunks are stored as nodes in the graph and linked in sequence so the original reading order is preserved.

**Embeddings.** An embedding model reads a chunk's text and produces a list of numbers, called a vector, that acts as a fingerprint for the meaning of the text, not just the words it contains. Texts that describe similar ideas get similar fingerprints. For example, "supply chain disruption" and "logistics bottleneck risk" produce nearly identical vectors because they describe related concepts, even though they share no keywords.

**Vector search.** Given a natural-language question, the system converts it into a vector using the same embedding model and then compares that vector against all the stored chunk vectors to find the closest matches. This is called semantic similarity search; it matches on meaning rather than exact keywords. The results are text passages ranked by how closely their meaning matches your question.

**The limitation of vector search alone.** Vector search returns isolated passages. You get the chunk text and a similarity score, but nothing about where the passage came from, what entities it mentions, or how it relates to other information in the corpus.

**Graph-enriched search.** A knowledge graph connects chunks to structured entities (documents, companies, products, risk factors) through typed relationships. After vector search finds relevant chunks, graph traversal follows those relationships to pull in structured context. The result is not just "here's a matching passage" but "here's a matching passage, filed by this company, mentioning these products, linked to these risk factors." That additional context grounds the LLM's answer in verified, structured data.

=== Example: SEC 10-K Filings

This lab applies the pattern above to SEC 10-K filings, the annual financial reports that public companies file with the Securities and Exchange Commission. A single filing can run tens of thousands of words covering business operations, risk factors, financial results, and more.

. Each filing is split into chunks and stored as `(:Chunk)` nodes linked by `NEXT_CHUNK` relationships.
. Each chunk is encoded into a 1024-dimensional embedding vector using Amazon Titan Text Embeddings V2 (`amazon.titan-embed-text-v2:0`).
. A vector index (`chunkEmbeddings`) enables semantic similarity search across all chunks.
. Graph relationships connect chunks back to their source `(:Document)`, which is linked to the `(:Company)` that filed it, and cross-links (`FROM_CHUNK`) tie chunks to the `(:Product)` and `(:RiskFactor)` entities they mention.

When you ask "What cybersecurity risks does Apple face?", vector search finds the most relevant passages. Graph-enriched search then follows relationships from those passages to return Apple as the filer, the specific products mentioned, and the risk factor classifications, all in a single retrieval step.

== Retrieval Strategies

GraphRAG is not a single retrieval method. It is a set of strategies you choose between based on the question. The first three find the right text; the last two bring in graph structure.

[cols="1,2,2"]
|===
| Strategy | How It Works | Best For

| **Vector Search**
| Embed the question, find similar chunks
| Conceptual, meaning-based questions

| **Full-text Search**
| Keyword match, ranked by Lucene/BM25
| Exact terms, names, acronyms

| **Hybrid Search**
| Run both, merge and re-rank results
| Meaning and exact keywords together

| **Graph-Enriched Search**
| Vector search plus graph traversal
| Questions needing entity context

| **Text2Cypher**
| LLM writes Cypher from the schema
| Counts, lists, specific lookups
|===

The two notebooks in this lab implement **Vector Search** (`VectorRetriever`) and **Graph-Enriched Search** (`VectorCypherRetriever`). **Full-text** and **Hybrid** search are demonstrated as Cypher in the xref:lab3-sample-queries.adoc[Lab 3 sample queries], and **Text2Cypher** is covered in xref:lab6.adoc[Lab 6].

=== VectorRetriever

Notebook 01 introduces the `VectorRetriever` from the neo4j-graphrag library. It wraps the vector index and handles embedding the query, running the similarity search, and formatting the results. Connected to an LLM via `GraphRAG`, it builds a complete question-answering pipeline. The results are chunk text ranked by cosine similarity: isolated passages with no graph context.

=== Full-text Search

Vector search matches meaning, but it can blur exact terms. "NVDA", a product codename, or a specific acronym may not sit close to your question in embedding space even when the chunk is an exact match. Full-text search covers that gap: a `search_chunks` fulltext index (Apache Lucene under the hood) matches keywords directly and ranks results by Lucene relevance (BM25-style) score. It also supports fuzzy matching for typos and boolean operators. The xref:lab3-sample-queries.adoc[sample queries] create the index and run keyword, fuzzy, and boolean searches.

=== Hybrid Search

Hybrid search runs vector and full-text search together and fuses the results, so you get semantic recall and exact-term precision at once. Because cosine similarity and Lucene relevance use different scales, the two result sets are normalized to a common range and then merged with a weight (*alpha*): re-ranking the combined list so the best matches from either signal rise to the top. The neo4j-graphrag library packages this as `HybridRetriever` and `HybridCypherRetriever`; the xref:lab3-sample-queries.adoc[sample queries] show the same normalize-and-merge re-ranking as plain Cypher.

=== VectorCypherRetriever

Notebook 02 extends vector search with the `VectorCypherRetriever`. After the vector index finds matching chunks, a custom Cypher retrieval query runs on each match to traverse the graph and pull in structured context:

[source,cypher]
----
MATCH (node)-[:FROM_DOCUMENT]->(doc:Document)
OPTIONAL MATCH (doc)<-[:FILED]-(company:Company)
WITH node, doc, score, company
RETURN node.text AS text,
       score,
       {document: doc.accessionNumber,
        filingType: doc.filingType,
        company: company.name,
        products: collect { MATCH (p:Product)-[:FROM_CHUNK]->(node) RETURN p.name },
        risks: collect { MATCH (r:RiskFactor)-[:FROM_CHUNK]->(node) RETURN r.name }
       } AS metadata
----

The query traverses from the matched chunk (`node`) to its source document and the company that filed it, then gathers the products and risk factors the chunk mentions. Products and risks are collected with separate `collect { ... }` subqueries scoped to the matched chunk (via `FROM_CHUNK`), not pulled in with additional top-level `MATCH` clauses. Matching two independent fan-outs in the same pattern (every product paired with every risk) would produce a cartesian product; the chunk-scoped `collect { ... }` subqueries keep each list scoped to what the chunk actually mentions and avoid that blow-up.

A custom `result_formatter` then maps each returned record into a `RetrieverResultItem`, separating the chunk text (passed to the LLM as context) from the structured metadata (available for programmatic inspection). Without a formatter, the retriever's default serializes the entire record into a single string, mixing the chunk text and metadata together.

The LLM now receives the matched chunk alongside the filing accession number, filing type, company name, product list, and risk factor labels, producing answers grounded in both unstructured text and structured knowledge graph relationships.

== What the Library Does Under the Hood

The neo4j-graphrag retrievers handle several steps internally so you can focus on the query rather than the plumbing. When you call a retriever, it:

1. **Embeds your question**: sends the text to the embedding model (Amazon Titan Text Embeddings V2) and gets back a 1024-dimensional vector.
2. **Queries the vector index**: runs a Cypher query against the `chunkEmbeddings` index using that vector.
3. **Traverses the graph** (Cypher retrievers only): executes the `retrieval_query` you provide to follow relationships from matched chunks to connected entities.
4. **Formats results for the LLM**: packages the retrieved text and metadata into a prompt-ready format.

In xref:lab6.adoc[Lab 6], you will do each of these steps yourself through MCP: writing the Cypher by hand, managing embeddings in `@tool` functions, and wiring the results back to the agent. Understanding what the library automates here will make the manual approach clearer.
