= Lab 4: Strands GraphRAG Agent and AgentCore

In Lab 3 you built retrieval pipelines where the developer decided which retriever to run for each question. This lab hands that decision to the model. You wrap the `VectorCypherRetriever` from Lab 3 as a Strands `@tool` function, build a Strands agent around it, and then deploy that agent to Amazon Bedrock AgentCore Runtime so every attendee has their own REST-invokable GraphRAG agent. This is the agent behind the workshop's opening hero-question demo.

== From Retriever to Agent

The `GraphRAG` pipeline in Lab 3 runs one retriever per call and returns an answer. It works well when you already know the retrieval strategy. Real questions are more varied. Some need a single passage, others need the company, its products, and its risk factors traversed from that passage.

A Strands agent moves that choice into a reasoning loop. You give the agent a tool and a description of what it does, and the model decides when to call it, reads the results, and either answers or calls again. This is the same `Agent` plus `BedrockModel` plus `@tool` pattern from the agent fundamentals material, now backed by a tool that searches your knowledge graph.

To wrap the retriever, you define a Python function that takes a natural-language query, runs the `VectorCypherRetriever` against the `chunkEmbeddings` index, traverses the graph to companies, products, and risk factors, and returns the formatted context. The `@tool` decorator turns that function into a tool the agent can call. The function's docstring tells the model what the tool retrieves and when to use it, so write it as instructions to the model rather than notes to a developer.

image::agent_tools.png[Strands agent with a GraphRAG tool,800]

When the agent receives a question like "What cybersecurity risks does Apple face?", the ReAct loop reasons that graph-enriched retrieval fits, calls the tool, reads the chunk text along with the filing company, products, and risk factors, and composes a grounded answer. The agent traverses the graph without any hardcoded retrieval logic in the caller.

For agent fundamentals (the ReAct loop, tools, and the Bedrock model wiring), see xref:appendix-agent.adoc[the agent fundamentals appendix].

== Deploying to Amazon Bedrock AgentCore Runtime

A local agent runs only while your notebook is open. To make it a service that other applications can call, you deploy it to Amazon Bedrock AgentCore Runtime.

=== What AgentCore Runtime Provides

AgentCore Runtime is serverless hosting for agents. Each agent session runs in its own isolated microVM, so sessions do not share memory or state. The runtime auto-scales with demand, exposes the agent through a REST endpoint, and leaves you with no servers, containers, or clusters to manage. You deploy agent code and get back an invokable endpoint.

=== Deploying with direct_code_deploy

This lab uses the `direct_code_deploy` path from the https://github.com/aws/bedrock-agentcore-starter-toolkit[bedrock-agentcore-starter-toolkit]. It packages your agent from source, with no Dockerfile to write:

* **The deployment package** is your agent code (`agent.py`) plus a `pyproject.toml` that declares its dependencies.
* **A `.bedrock_agentcore.yaml` config** specifies the entrypoint, the runtime, and the IAM execution role the agent assumes at run time.
* **Running the deploy** packages the code, uploads it to S3, and creates the AgentCore runtime for you.

Once the runtime is created, you invoke the agent through its REST endpoint. From Python that is the `bedrock-agentcore` boto3 client calling `invoke_agent_runtime` with the agent ARN and your prompt. You can also invoke it from the `agentcore` CLI. Every attendee ends up with their own deployed agent ARN they can call on demand.

=== IAM and Hosted Environments

The AgentCore deployment depends on IAM resources that the workshop administrator provisions ahead of time, including the execution role the runtime assumes. See xref:admin-setup.adoc[the admin setup guide] for what is created.

NOTE: In hosted OneBlink environments the deploy step may lack the permissions to create the runtime. If that happens, review the deployment code in the notebook to understand each step, then run the full deploy later in your own AWS account where you hold the required permissions.
