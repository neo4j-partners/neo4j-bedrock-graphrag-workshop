= Lab 5: Agent Memory with Neo4j

This lab adds memory to the GraphRAG agent from xref:lab4.adoc[Lab 4]. The agent gains short-term memory for recent conversation turns and long-term memory for durable entities, facts, and preferences, both stored in the same Neo4j Aura instance that holds the SEC 10-K knowledge graph. The result is an agent that carries context across a conversation instead of answering every question from a blank slate.

The lab ships as two notebooks in `Lab_5_Agent_Memory/`: `01_short_term_memory.ipynb` for the conversational recall layer and `02_long_term_memory.ipynb` for the durable knowledge layer.

== Why Stateless Agents Fail

The Lab 4 agent is stateless. Each invocation receives only the current question, runs its GraphRAG tool, and returns an answer. Nothing from the previous turn survives into the next one.

That works for single, self-contained questions. It breaks in conversation. Consider three questions in a row:

. "Tell me about Apple's risk factors."
. "What about their competitors?"
. "Summarize what we discussed."

A stateless agent handles the first question and loses it. On the second question it sees only "What about their competitors?" with no idea who "their" refers to. On the third it has nothing to summarize. Human conversation depends on shared context that accumulates turn by turn, and a stateless agent throws that context away after every call.

== Short-Term and Long-Term Memory

The https://github.com/neo4j-labs/agent-memory[neo4j-agent-memory] library gives the agent two kinds of memory backed by Neo4j:

* **Short-term memory** holds the recent conversation turns verbatim: the questions asked and the answers given. This is what lets the agent resolve "their" to Apple, because the prior turn is still available.
* **Long-term memory** holds entities and facts extracted from the conversation over time. Instead of storing raw text, it distills durable knowledge such as "the user is interested in Apple" or "Apple competes with Samsung," which persists beyond the current session.

Together they mirror how people converse. Short-term memory tracks the thread of the current discussion, and long-term memory retains what matters after the discussion ends.

== The Memory Graph Schema

The memory layer stores its state as its own small graph. Short-term memory uses two node types:

* **`Conversation`**: one node per conversation session, the root that ties the turns together, linked to its turns by `HAS_MESSAGE`.
* **`Message`**: one node per turn, holding the question or answer text, chained in order by `NEXT_MESSAGE`.

Long-term memory adds three more:

* **`Entity`**: a durable thing worth remembering, such as a company, deduplicated on write.
* **`Fact`**: a subject, predicate, object statement, such as "Apple COMPETES_WITH Microsoft."
* **`Preference`**: how the user likes their answers shaped.

These nodes live in the *same* Aura instance as the SEC 10-K knowledge graph. Open Neo4j Browser after running the demo and you will see the memory nodes sitting alongside the `Company`, `Product`, `RiskFactor`, and `Chunk` nodes from the 10-K graph, all in one database.

== One Database, Two Roles

The same Neo4j Aura instance plays two roles at once:

* **Knowledge graph** for GraphRAG retrieval: the companies, products, risk factors, documents, and chunks the agent searches to answer questions.
* **Memory store** for agent state: the conversation and entity graph that records what has been discussed.

Keeping both in one database means the agent reads its domain knowledge and its conversational context from a single connection. There is no separate memory service to provision, and the memory graph can reference the same entities the knowledge graph already models.

The memory layer reuses the infrastructure Part 2 already configured. It connects to the same Aura instance and uses the same embedding model, Amazon Titan Text Embeddings V2 (`bedrock/amazon.titan-embed-text-v2:0`), which produces 1024-dimensional vectors. No new models and no new database are required.

== What You Build

You take the Lab 4 Strands GraphRAG agent and wrap it with neo4j-agent-memory across two notebooks.

`01_short_term_memory.ipynb`, the conversational recall layer:

* Configure a memory client against the existing Aura instance, using Titan Text Embeddings V2 for embeddings.
* After each turn, write the question and answer to short-term memory with `add_message`.
* Before each invocation, pull relevant prior context with `get_context` and inject it into the prompt so the agent reasons with the full conversation, not just the latest question.

`02_long_term_memory.ipynb`, the durable knowledge layer:

* Persist entities, facts, and preferences with `add_entity`, `add_fact`, and `add_preference`.
* Recall them from a brand-new session with `search_entities` and `long_term.get_context`, showing the knowledge is not tied to a single conversation.

The GraphRAG tool from Lab 4 stays the same. Memory wraps around it. Notebook `01` imports the Lab 4 agent directly rather than rebuilding it, so everything new is the memory layer.

== What You See

Run the three-turn demo and watch memory change the agent's behavior:

* **Turn 1: "Tell me about Apple's risk factors."** The agent runs GraphRAG retrieval against the 10-K graph and answers from the filing data. It also writes this turn to short-term memory.
* **Turn 2: "What about their competitors?"** The agent reads short-term memory, resolves "their" to Apple from the previous turn, and answers about Apple's competitors. A stateless agent could not do this.
* **Turn 3: "Summarize what we discussed."** The agent draws on the accumulated conversation to return a coherent summary that spans both prior turns, covering Apple's risk factors and its competitors.

Then open Neo4j Browser. The memory nodes appear in the same database as the 10-K graph, so you can see the conversation state and the domain knowledge side by side.

== Going Further: Reasoning Traces

Short-term and long-term memory cover what the agent discussed and what it knows. A third pillar, *reasoning traces*, is the observability and audit layer: a record of the steps the agent took and the entities each step touched. The two notebooks in this lab do not use it, but it is worth knowing the shape.

`neo4j-agent-memory` records a trace as a `ReasoningTrace` node with ordered `ReasoningStep` nodes, and each step links to the entities it referenced with a `TOUCHED` edge. That makes an audit one hop wide. To find every reasoning step that touched Apple:

[source,cypher]
----
MATCH (e:Entity {name: 'Apple'})<-[:TOUCHED]-(s:ReasoningStep)<-[:HAS_STEP]-(rt:ReasoningTrace)
RETURN rt, s, e
----

Because the trace, the steps, and the domain entities are all in one graph, you can answer "why did the agent say that?" by traversing from an answer back to the steps and the data that produced it. This is where memory in a graph pays off over memory in a flat log.
