Follow these notebooks to build retrieval pipelines against your knowledge graph, progressing from pure vector search to graph-enriched retrieval to hybrid search. The unstructured half (chunks, Titan v2 embeddings, and the `chunkEmbeddings` index) is already in place from the Lab 1 seed load, so the notebooks start directly with retrieval.

* **Vector Search**: Use `VectorRetriever` to find semantically similar chunks and generate answers with the `GraphRAG` pipeline

== Walkthrough

=== Notebook 01: Vector Retriever

. **Connect with query notifications disabled.** The retrievers call the server procedure `db.index.vector.queryNodes`, which Aura now flags as deprecated. Passing `notifications_min_severity='OFF'` when you build the driver stops it from logging one deprecation WARNING per search:
+
[source,python]
----
# notifications_min_severity='OFF' tells the server not to send query
# notifications. The retrievers below run db.index.vector.queryNodes, which Aura
# now flags as a deprecation; without this the driver logs one WARNING per search.
driver = GraphDatabase.driver(
    NEO4J_URI,
    auth=(NEO4J_USERNAME, NEO4J_PASSWORD),
    notifications_min_severity='OFF',
)
driver.verify_connectivity()
----
+
. **Search for chunks.** Initialize a `VectorRetriever` over the `chunkEmbeddings` index and call `search(query_text=..., top_k=5)` to get the most similar chunks. Each result carries its cosine similarity in `item.metadata['score']`.
. **Answer with the GraphRAG pipeline and inspect the context.** Wrap the retriever in `GraphRAG`. Pass `retriever_config={'top_k': N}` to control how many chunks are retrieved, and `return_context=True` to attach the retrieved chunks to the response so you can see exactly what the LLM received via `response.retriever_result.items`:
+
[source,python]
----
rag = GraphRAG(llm=llm, retriever=vector_retriever)

query = "What are the key risk factors mentioned in Apple's 10-K filing?"
response = rag.search(query, retriever_config={'top_k': 5}, return_context=True)

print(f'Query: "{query}"')
print(f'Chunks retrieved: {len(response.retriever_result.items)}\n')
print('Answer:')
print(response.answer)
----

=== Notebook 02: VectorCypher Retriever

. **Define the retrieval query.** A Cypher query runs on each matched chunk. It receives the `node` and `score` variables, traverses to the source document and the company that filed it, and gathers products and risk factors with chunk-scoped `collect { ... }` subqueries. See the full query and why the subqueries avoid a cartesian product in xref:lab3.adoc[Lab 3: Semantic Search and GraphRAG].
. **Format each record.** Pass a `result_formatter` so the retriever separates the chunk text (the `content` sent to the LLM) from the structured graph metadata. Without a formatter, the default serializes the entire record into a single string:
+
[source,python]
----
def format_record(record: neo4j.Record) -> RetrieverResultItem:
    """Separate chunk text (content for LLM) from structured graph metadata."""
    metadata = record.get("metadata") or {}
    metadata["score"] = record.get("score")
    return RetrieverResultItem(
        content=record.get("text", ""),
        metadata=metadata,
    )

vector_cypher_retriever = VectorCypherRetriever(
    driver=driver,
    index_name='chunkEmbeddings',
    embedder=embedder,
    retrieval_query=RETRIEVAL_QUERY,
    result_formatter=format_record,
)
----
+
. **Search and inspect the enriched metadata.** Each `item.metadata` now carries `company`, `products`, `risks`, and `score` alongside the chunk text in `item.content`. As in Notebook 01, building a `GraphRAG` pipeline and calling `search(query, retriever_config={'top_k': 5}, return_context=True)` exposes the enriched matches through `response.retriever_result.items`.

=== Notebook 03: Hybrid Retriever

. **Create the full-text index.** The Lab 1 seed load built the `chunkEmbeddings` vector index and a `search_entities` index on entity names, but not a full-text index over chunk text. Create `search_chunks` before searching, and wait for it to come online so the queries below do not race the build:
+
[source,python]
----
driver.execute_query(
    "CREATE FULLTEXT INDEX search_chunks IF NOT EXISTS FOR (c:Chunk) ON EACH [c.text]"
)
driver.execute_query("CALL db.awaitIndexes(300)")
----
+
. **Run keyword search.** Query the index directly with `db.index.fulltext.queryNodes('search_chunks', ...)` to see chunks ranked by Lucene relevance. Unlike vector search, this matches terms literally, which is strong on exact names, tickers, and acronyms.
. **Fuse the two signals with `HybridRetriever`.** Pass both index names and the embedder. On `search`, the retriever embeds the query for the vector arm, passes the same text as keywords to the full-text arm, and merges the two result sets:
+
[source,python]
----
hybrid_retriever = HybridRetriever(
    driver=driver,
    vector_index_name='chunkEmbeddings',
    fulltext_index_name='search_chunks',
    embedder=embedder,
    return_properties=['text'],
)
----
+
. **Compare the re-rankers.** Run the same query with `ranker=HybridSearchRanker.NAIVE` (default; max normalized score per chunk) and with `ranker=HybridSearchRanker.LINEAR` at `alpha=0.9` versus `alpha=0.1`. The `linear` ranker blends the arms as `alpha * vector + (1 - alpha) * fulltext`; a high `alpha` favors meaning, a low `alpha` favors exact keywords, and the ranking visibly shifts between them.
. **Add graph traversal with `HybridCypherRetriever`.** It takes the same two indexes plus the `retrieval_query` and `result_formatter` from Notebook 02, so hybrid search finds the chunks and the Cypher traversal enriches each match with its filing, company, products, and risk factors. Ranker options pass through `retriever_config` when wrapped in a `GraphRAG` pipeline.

=== Reference: How the Vector Index Was Built

The `chunkEmbeddings` index and its embeddings were created by the Lab 1 seed load; xref:lab2.adoc[Lab 2] rebuilds the same pipeline in an isolated sandbox. Two neo4j-graphrag index utilities do the work.

`upsert_vectors` stores each embedding on its chunk node. The `ids` list holds Neo4j element ids in the same order as the `embeddings` list, so the vector written to each node matches the chunk it was generated from:

[source,python]
----
upsert_vectors(
    driver,
    ids=chunk_ids,
    embedding_property='embedding',
    embeddings=chunk_embeddings,
)
----

Those element ids come from returning `elementId()` ordered by the chunk index, which keeps the id list aligned with the embedding list:

[source,cypher]
----
MATCH (ch:DemoChunk:Demo)
RETURN elementId(ch) AS id
ORDER BY ch.index
----

`create_vector_index` then defines the index over the embedding property, matching the 1024 dimensions of Amazon Titan Text Embeddings V2 and cosine similarity:

[source,python]
----
create_vector_index(
    driver,
    name=DEMO_INDEX,
    label='DemoChunk',
    embedding_property='embedding',
    dimensions=1024,
    similarity_fn='cosine',
)
----
