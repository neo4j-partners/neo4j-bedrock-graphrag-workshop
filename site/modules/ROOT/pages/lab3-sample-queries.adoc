= Lab 3: Sample Queries

These queries let you explore the unstructured half loaded by the Lab 1 seed load: Document and Chunk nodes, the `chunkEmbeddings` vector index, and `FROM_CHUNK` cross-links. They return results once the seed load has been run.

TIP: For structured graph queries against the entity data from the Lab 1 seed load, see the xref:sample-queries.adoc[Sample Cypher Queries] page.

== Document-Chunk Structure

View all documents and their chunk counts:

[source,cypher]
----
MATCH (d:Document)
OPTIONAL MATCH (d)<-[:FROM_DOCUMENT]-(c:Chunk)
RETURN d.source AS document, count(c) AS chunks
ORDER BY chunks DESC
----

NOTE: `OPTIONAL MATCH` keeps documents even if chunking has not completed. Each Document represents one SEC 10-K filing.

Browse the first chunks of a document:

[source,cypher]
----
MATCH (c:Chunk)-[:FROM_DOCUMENT]->(d:Document)
WITH c, d ORDER BY c.index LIMIT 10
RETURN c.index AS chunkIndex,
       substring(c.text, 0, 120) AS preview,
       d.source AS document
----

NOTE: `substring()` truncates long text for readable output. Chunks are ordered by their `index` property, which reflects their position in the original filing.

Walk the chunk chain:

[source,cypher]
----
MATCH (c:Chunk)-[:FROM_DOCUMENT]->(d:Document)
OPTIONAL MATCH (c)-[:NEXT_CHUNK]->(next:Chunk)
WITH c, next, d ORDER BY c.index LIMIT 10
RETURN c.index AS chunkIndex,
       substring(c.text, 0, 80) AS preview,
       next.index AS nextChunkIndex,
       d.source AS document
----

NOTE: `OPTIONAL MATCH` on NEXT_CHUNK keeps the last chunk in the chain (which has no successor). The NEXT_CHUNK relationship preserves reading order so that adjacent context can be retrieved alongside vector matches.

== Vector Similarity Search

IMPORTANT: Requires the `chunkEmbeddings` vector index (created by the Lab 1 seed load).

Find chunks similar to a random seed chunk (no API key needed):

[source,cypher]
----
MATCH (seed:Chunk)
WHERE seed.embedding IS NOT NULL
WITH seed, rand() AS r ORDER BY r LIMIT 1
CALL db.index.vector.queryNodes(
    'chunkEmbeddings', 6, seed.embedding
) YIELD node, score
WHERE node <> seed
WITH seed, node, score ORDER BY score DESC LIMIT 5
RETURN substring(seed.text, 0, 100) AS seedText,
       score AS similarity,
       substring(node.text, 0, 100) AS matchText
----

NOTE: Picks a random chunk and uses its stored embedding to find the most similar chunks in vector space. No embedding API call is needed because the query reuses embeddings already stored on Chunk nodes. `WHERE node <> seed` excludes the seed from its own results.

Vector search with document context:

[source,cypher]
----
MATCH (seed:Chunk)
WHERE seed.embedding IS NOT NULL
WITH seed, rand() AS r ORDER BY r LIMIT 1
CALL db.index.vector.queryNodes(
    'chunkEmbeddings', 6, seed.embedding
) YIELD node, score
WHERE node <> seed
WITH seed, node, score ORDER BY score DESC LIMIT 5
MATCH (node)-[:FROM_DOCUMENT]->(d:Document)
RETURN substring(seed.text, 0, 80) AS seedText,
       score AS similarity,
       d.source AS document,
       substring(node.text, 0, 80) AS matchText
----

NOTE: Enriches vector results by traversing FROM_DOCUMENT to include the source filing. This is the same pattern used by the `VectorCypherRetriever` in Lab 3 Notebook 02: vector search finds the chunk, then graph traversal gathers context.

== Graph-Enriched Search

These queries combine vector search with graph traversal, demonstrating the GraphRAG patterns covered in Lab 3.

'''

=== Chunk to Company (the GraphRAG traversal)

From a vector match, traverse to the filing company:

[source,cypher]
----
MATCH (seed:Chunk)
WHERE seed.embedding IS NOT NULL
WITH seed, rand() AS r ORDER BY r LIMIT 1
CALL db.index.vector.queryNodes(
    'chunkEmbeddings', 6, seed.embedding
) YIELD node, score
WHERE node <> seed
WITH seed, node, score ORDER BY score DESC LIMIT 5
MATCH (node)-[:FROM_DOCUMENT]->(d:Document)<-[:FILED]-(c:Company)
RETURN substring(seed.text, 0, 80) AS seedText,
       score AS similarity,
       c.name AS company,
       c.ticker AS ticker,
       d.source AS document,
       substring(node.text, 0, 80) AS matchText
----

NOTE: This is the core GraphRAG pattern. Vector search finds relevant chunks, then `FROM_DOCUMENT` reaches the Document and `FILED` reaches the Company. The agent receives both the text and the structured entity context. This traversal path is what the `VectorCypherRetriever`'s `retrieval_query` parameter automates in Notebook 02.

=== Chunk to Company to Risk Factors

Extend the traversal to include the company's risk factors:

[source,cypher]
----
MATCH (seed:Chunk)
WHERE seed.embedding IS NOT NULL
WITH seed, rand() AS r ORDER BY r LIMIT 1
CALL db.index.vector.queryNodes(
    'chunkEmbeddings', 6, seed.embedding
) YIELD node, score
WHERE node <> seed
WITH seed, node, score ORDER BY score DESC LIMIT 3
MATCH (node)-[:FROM_DOCUMENT]->(d:Document)<-[:FILED]-(c:Company)
OPTIONAL MATCH (c)-[:FACES_RISK]->(r:RiskFactor)
RETURN c.name AS company,
       substring(node.text, 0, 100) AS matchText,
       score AS similarity,
       collect(r.name) AS riskFactors
----

NOTE: Extends the base GraphRAG pattern by following FACES_RISK from the company. `OPTIONAL MATCH` keeps results even for companies with no risk factors loaded. `collect()` gathers all risk factors into a list per company.

=== Adjacent Chunk Retrieval

Retrieve surrounding chunks for broader context:

[source,cypher]
----
MATCH (seed:Chunk)
WHERE seed.embedding IS NOT NULL
WITH seed, rand() AS r ORDER BY r LIMIT 1
CALL db.index.vector.queryNodes(
    'chunkEmbeddings', 6, seed.embedding
) YIELD node, score
WHERE node <> seed
WITH seed, node, score ORDER BY score DESC LIMIT 3
OPTIONAL MATCH (prev:Chunk)-[:NEXT_CHUNK]->(node)
OPTIONAL MATCH (node)-[:NEXT_CHUNK]->(next:Chunk)
RETURN substring(node.text, 0, 80) AS matchText,
       score AS similarity,
       node.index AS chunkIndex,
       prev.index AS prevIndex,
       next.index AS nextIndex,
       substring(COALESCE(prev.text, ''), 0, 60) AS prevPreview,
       substring(COALESCE(next.text, ''), 0, 60) AS nextPreview
----

NOTE: NEXT_CHUNK relationships form a linked list that preserves the original reading order. Retrieving the previous and next chunks alongside the vector match gives the agent a wider context window. `COALESCE` handles the first and last chunks in a chain, which have no predecessor or successor.

== Full-text Keyword Search

Full-text indexes enable keyword-based search alongside vector similarity. The `search_entities` index was already created by the xref:lab1.adoc[Lab 1 seed load]. The queries below also require a `search_chunks` index on Chunk text, which is not created until you run the setup query below.

TIP: Notebook 03 (`03_hybrid_retriever.ipynb`) creates the same `search_chunks` index and runs keyword search through the neo4j-graphrag library. The queries here show the raw Cypher underneath, plus fuzzy and boolean variants.

=== Setup: Create Full-text Index on Chunks

[source,cypher]
----
CREATE FULLTEXT INDEX search_chunks IF NOT EXISTS
FOR (c:Chunk) ON EACH [c.text]
----

NOTE: This index uses Apache Lucene under the hood. `IF NOT EXISTS` makes the statement safe to re-run. Allow a few seconds for indexing to complete before running the queries below.

=== Keyword Search

Search chunks for a specific term:

[source,cypher]
----
CALL db.index.fulltext.queryNodes('search_chunks', 'cybersecurity')
YIELD node, score
RETURN score,
       substring(node.text, 0, 200) AS content
ORDER BY score DESC
LIMIT 5
----

NOTE: Full-text search returns chunks ranked by Lucene relevance score. Terms are matched as keywords, not by semantic meaning.

Fuzzy search (catches misspellings):

[source,cypher]
----
CALL db.index.fulltext.queryNodes('search_chunks', 'regulatry~')
YIELD node, score
RETURN score,
       substring(node.text, 0, 200) AS content
ORDER BY score DESC
LIMIT 5
----

NOTE: The `~` operator enables fuzzy matching, finding "regulatory" even when spelled as "regulatry". Useful for user-facing search where typos are common.

Boolean keyword search:

[source,cypher]
----
CALL db.index.fulltext.queryNodes('search_chunks', 'supply AND chain AND disruption')
YIELD node, score
RETURN score,
       substring(node.text, 0, 200) AS content
ORDER BY score DESC
LIMIT 5
----

NOTE: Boolean operators (AND, OR, NOT) control how keywords combine. `AND` requires all terms to appear in the chunk.

Search entity names:

[source,cypher]
----
CALL db.index.fulltext.queryNodes('search_entities', 'NVIDIA')
YIELD node, score
RETURN labels(node)[0] AS type, node.name AS name, score
ORDER BY score DESC
LIMIT 10
----

NOTE: The `search_entities` index covers Company, Product, and RiskFactor names. This finds entities by name rather than searching filing text.

=== Full-text Search with Entity Enrichment

Find chunks by keyword, then traverse to the company and its products:

[source,cypher]
----
CALL db.index.fulltext.queryNodes('search_chunks', 'artificial intelligence')
YIELD node, score
WITH node, score ORDER BY score DESC LIMIT 5
MATCH (node)-[:FROM_DOCUMENT]->(d:Document)<-[:FILED]-(c:Company)
OPTIONAL MATCH (c)-[:OFFERS]->(p:Product)
RETURN c.name AS company,
       score AS relevance,
       collect(DISTINCT p.name) AS products,
       substring(node.text, 0, 120) AS excerpt
----

NOTE: Combines full-text keyword search with the same graph traversal pattern used in vector-based GraphRAG. The difference is the starting point: full-text search matches by keywords while vector search matches by semantic meaning. Both traverse the same graph structure to enrich results.

== Hybrid Search

Hybrid search fuses the two previous strategies over the same chunks: vector similarity catches meaning and paraphrase, while full-text keyword search catches exact names, tickers, and acronyms that embeddings can blur. The catch is that the two signals use different score scales (cosine similarity is roughly 0 to 1; Lucene relevance is unbounded), so the results have to be re-ranked onto a common scale before they can be merged.

IMPORTANT: Requires both the `chunkEmbeddings` vector index (Lab 1 seed load) and the `search_chunks` full-text index (created above).

TIP: Notebook 03 (`03_hybrid_retriever.ipynb`) does this fusion for you with `HybridRetriever` and `HybridCypherRetriever`, exposing the same choice of ranker (`NAIVE` versus `LINEAR` with an `alpha` weight). The query below shows the normalize-and-merge mechanics as raw Cypher.

=== Merge and Re-rank Two Signals

Run both searches, normalize each score to 0 to 1, then combine with a weighted sum:

[source,cypher]
----
// Gather candidates from both signals. The vector arm reuses a random chunk's
// stored embedding so no embedding API call is needed; the full-text arm matches
// a keyword. Each arm returns the same three columns so the UNION lines up.
CALL {
    MATCH (seed:Chunk) WHERE seed.embedding IS NOT NULL
    WITH seed, rand() AS r ORDER BY r LIMIT 1
    CALL db.index.vector.queryNodes('chunkEmbeddings', 10, seed.embedding)
    YIELD node, score
    RETURN node, score AS vScore, 0.0 AS tScore
  UNION
    CALL db.index.fulltext.queryNodes('search_chunks', 'cybersecurity risk')
    YIELD node, score
    RETURN node, 0.0 AS vScore, score AS tScore
}
// Collapse duplicates: a chunk found by both arms keeps its best score from each.
WITH node, max(vScore) AS vScore, max(tScore) AS tScore
WITH collect({node: node, vScore: vScore, tScore: tScore}) AS rows
// Find the top score in each signal so we can normalize onto a shared 0 to 1 scale.
WITH rows,
     reduce(mx = 0.0, x IN rows | CASE WHEN x.vScore > mx THEN x.vScore ELSE mx END) AS vMax,
     reduce(mx = 0.0, x IN rows | CASE WHEN x.tScore > mx THEN x.tScore ELSE mx END) AS tMax
UNWIND rows AS x
WITH x.node AS node,
     CASE WHEN vMax > 0 THEN x.vScore / vMax ELSE 0.0 END AS vNorm,
     CASE WHEN tMax > 0 THEN x.tScore / tMax ELSE 0.0 END AS tNorm
RETURN substring(node.text, 0, 120) AS content,
       round(vNorm, 3) AS semanticScore,
       round(tNorm, 3) AS keywordScore,
       round(0.5 * vNorm + 0.5 * tNorm, 3) AS hybridScore
ORDER BY hybridScore DESC
LIMIT 5
----

NOTE: This is the re-ranking that `HybridRetriever`'s `LINEAR` ranker in neo4j-graphrag does for you; its default `NAIVE` ranker normalizes each signal the same way, then simply takes the higher of the two normalized scores per node instead of the weighted blend. The `LINEAR` ranker normalizes each signal independently, then merges them with a weight `alpha` (the vector weight, with `1 - alpha` on keywords; here an even split at `alpha = 0.5`). Raise `alpha` to favor meaning, lower it to favor exact terms. In the library both arms run against the same user question (embedded for the vector arm, passed as keywords to the full-text arm); this example reuses a stored embedding for the vector arm so it runs without an API key, so read it as a demonstration of the fusion mechanics rather than a single coherent question.
